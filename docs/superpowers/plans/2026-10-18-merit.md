# MERIT Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the `merit` CLI — a deterministic validator, anchoring engine, transactional write path and report generator that makes it impossible to commit a requirement whose evidence does not resolve verbatim to an immutable, hash-pinned source bundle.

**Architecture:** A Python package whose schemas and prompts ship as package data, so a project repo holds only data and a ~20-line `AGENTS.md`. Every validation rule is a numbered check registered under its own ID. The agent never writes a governed file: it writes a *proposal*, and `merit apply` allocates IDs, anchors quotes, validates and commits atomically or not at all.

**Tech Stack:** Python 3.11+, `pyyaml`, `jsonschema` (runtime deps — nothing else). `pytest` for tests. `.docx` and `.vtt` parsing via stdlib `zipfile` + `xml.etree`.

**Spec:** `docs/superpowers/specs/2026-10-18-merit-design.md` (rev 5)

## How to execute every task

**This loop applies to all 22 tasks and is not repeated in them.** Each task lists only what is distinctive: its files, its dependencies, the tests that pin its behaviour, the implementation decisions a signature and test do not settle, and its exit criterion.

1. Write the task's tests. They must fail.
2. Run them and confirm they fail **for the stated reason**, not an import error standing in for a real assertion.
3. Implement until they pass, writing nothing the tests and signatures do not require.
4. Run the task's tests, then the full suite.
5. Commit. Attribute per your own tooling's convention — this plan mandates no trailer (see Global Constraints).

Where a task lists an **AGENTS.md trigger**, update the tool's `AGENTS.md` before committing.

## Global Constraints

- Runtime dependencies are **exactly** `pyyaml` and `jsonschema` (D2). `pytest` is a dev dependency only.
- Python **3.11+** (stdlib `tomllib`). Target OS includes Windows 11 — never create symlinks; use pathlib.
- **JSON Schema covers structure, types, enums and patterns only.** Every cross-field rule lives in a numbered check, or a fixture pinned to V6 fails V3 first.
- Exit codes: `0` success · `1` validation failure · `2` usage error · `3` anchor failure · `4` environment error.
- ID patterns: `^REQ-[A-Z]{2,6}-\d{4}$`, `^CAN-\d{4}$`, `^ISS-\d{4}$`, `^DEC-\d{4}$`, `^SUP-\d{4}$`. `schema_version: 1` everywhere.
- **The source bundle is the unit of integrity** (D11). Nothing in a sidecar is editable after ingest.
- **`merit apply` is the only write path** for `requirements/`, `candidates/`, `issues/`, `decisions/`, `supersessions/`, `baselines/` (D14, G8). **`merit ingest` is the sole exception** (D19): it owns `sources/` and may only *create* there.
- **`apply` validates the staged tree against the real repo's config and git history** (D17).
- **A provisional decision is a valid state.** V9 permits a self-note with no `confirmed_by`; V8 blocks it from a baseline.
- **A confirmation requires evidence, not a name** (D20). `confirmed_by` is meaningless without a `confirmation_record`.
- **Derived, never stored:** `open_issues`, `awaiting_confirmation`.
- No code path merges or tags (D6). D6 grep tests must exempt `merge_base`.
- `proposals/` is gitignored, never validated, removed after a successful apply.
- All file I/O is explicitly UTF-8.
- **Attribution:** each implementer attributes commits per their own tooling's convention. No fixed co-author trailer is mandated — G5 is model-agnosticism, and a hardcoded trailer would misattribute other implementers' work.

## Review Focus

Five input classes the spec implies but does not pin.

1. **CRLF line endings and UTF-8 BOM** — the target is Windows. If either reaches the hash, every bundle check fails on files nobody edited. → **Task 4**
2. **Unicode punctuation in quotes** — an agent retyping emits `'` where the transcript has `'`. Expect failure naming the character and codepoint, not a bare "not found". → **Task 10**
3. **Version pin mismatch** — expect exit 4 naming both versions, never silent validation under different rules. → **Task 2**
4. **Missing or empty artefact directories** — expect a clean finding or clean pass, never a traceback. → **Task 7**
5. **ID allocation across a rolled-back transaction** — a proposal failing at operation 3 of 5 must consume no IDs. → **Task 15**

## Curating the tool's own `AGENTS.md`

Spec §5.17. A context-economy instrument: a future session should recover non-obvious invariants without re-reading the codebase.

**Belongs**: cross-module invariants (schemas carry no cross-field rules; every check registers under its ID; `open_issues` and `awaiting_confirmation` are derived; the tool never merges or tags; `apply` is the only governed write path; `ingest` is the one create-only exception) · decisions that **reversed** an earlier approach, with one line of why · where non-obvious things live (schemas and prompts are package data; the argparse tree is the source of truth for the agent manual) · the test command and which fixtures must pass versus fail.

**Does not belong**: anything `grep` answers, narration, status updates, changelogs.

**Four update triggers**: after adding or renumbering a check · after changing an interface consumed by more than one module · **after a decision that reverses an earlier one** · when a session had to re-derive something already settled.

**Under ~200 lines.** Past that it costs more context than it saves. Task 25 is a cut pass.

### Task 15 — The transactional write path

**Files:** `src/merit/apply/{proposal,operations,transaction}.py` · `tests/test_apply.py`
**Depends on:** 14
**Fixtures:** `apply_mutating_a_historical_source`, `apply_removing_an_id`

Proposal parsing, the ten operation handlers and the transaction are **one task**: the transaction's success tests cannot run without handlers, and the handlers cannot be exercised without the transaction.

- [ ] **Proposal tests:** a proposal naming an explicit new ID is rejected — merit owns IDs · an unknown operation is a usage error · every operation in the schema has a handler.
- [ ] **Transaction tests:** a successful apply writes artefacts and anchors them · the full check suite runs before anything is committed · **a failing proposal leaves the repo byte-identical** · the failure names the failing operation index · the applied proposal is removed on success · **Review Focus 5** — a rolled-back transaction consumes no IDs, so the next apply allocates `REQ-SMP-0008`, not `0009`.
- [ ] **Context tests (D17):** `apply_mutating_a_historical_source` fails **V2** and `apply_removing_an_id` fails **V4** *through apply* — both pass vacuously without a context root, which is the bug · staged validation resolves the real repo's comparison point and loads config from the real repo.
- [ ] **Operation tests:** `add_requirement` allocates and anchors, and is rejected without evidence · `add_candidate` rejects an `evidence` field · `add_issue` requires two evidence entries · **`add_decision` on a self-note succeeds and is provisional** (it must not roll back) and warns that it is · **`confirm_decision` requires a `confirmation_record`**, rejects one sourced from a self-note, rejects a speaker mismatch, rejects the note's own author, and on success moves the issue to `resolved` · `promote_candidate` requires evidence at promotion and sets both link fields without deleting the candidate · `set_status` requires reasons and cannot baseline past an open issue · `dismiss_issue` requires a reason · `record_supersession` writes a new `SUP` file and **mutates no sidecar** (D15).
- [ ] **Implement `proposal.py`** — parse and schema-validate; reject new-artefact IDs.
- [ ] **Implement `transaction.py`** — copy governed directories into a staging tree, apply operations, anchor every quote, run `run_checks(staging, context_root=repo_root)`, move into place only on success. `allocate_id` derives from staging state so a rollback consumes nothing. Delete the applied proposal on success.
- [ ] **Implement the ten handlers** — `add_requirement`, `add_candidate`, `add_issue`, `add_decision`, `confirm_decision`, `promote_candidate`, `set_status`, `dismiss_issue`, `add_acceptance_criterion`, `record_supersession`. Each takes the staging tree and one operation dict and returns the paths it wrote.

**Exit (B4):** a proposal creates requirements, candidates and issues with no direct YAML write; a failing one leaves the repo byte-identical; an unevidenced confirmation is refused.
**AGENTS.md trigger 2** — `run_checks` gained `context_root`, consumed by three modules.

### Task 22 — Reusable workflow and release bootstrap

**Files:** `.github/workflows/{merit-validate.yml,release.yml,test.yml}`, `docs/RELEASING.md` · `tests/test_release.py`
**Depends on:** 7

Two constraints bind. **A tag cannot contain a file committed after it**, so the reusable workflow is authored *here*, in the same commit that gets tagged — rev 4 split these across tasks and made the order unfollowable. - [ ] **Tests:** `pyproject` version matches `__version__` · the release workflow builds a wheel and attaches it to the tag · `RELEASING.md` states the order with `commit` before `tag` before `publish` · the resolved tag SHA **contains `merit-validate.yml`** · the reusable workflow installs by **URL plus a 64-hex SHA-256 digest check**, and contains no bare `pip install merit==` (nothing would resolve it) and no reference to `merit.toml` (the downgrade path §5.1 identifies).
- [ ] **Write `merit-validate.yml`** — the reusable workflow, fetching the wheel by explicit URL and verifying `sha256sum -c` **before** `pip install ./merit.whl`, then running `merit validate`. - [ ] **Write `release.yml`** — on a `v*` tag, build the wheel and attach it.
- [ ] **Write `docs/RELEASING.md`** — commit package **and** workflow together → tag that commit → publish the wheel and record its digest → `merit init` resolves the tag's SHA at scaffold time.
- [ ] **Write the tool's `test.yml`** — `pytest` on push and PR.
- [ ] **Cut `v0.1.0`** against a commit already containing `merit-validate.yml`; confirm the artefact exists and the digest matches.
